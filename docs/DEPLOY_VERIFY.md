# QRonus: проверка фактически развёрнутого коммита на Render

## Зачем

Зелёный GitHub Actions означает, что исходники успешно прошли проверки,
но **не означает**, что Render уже развернул этот же коммит.

Для проверки версии используйте отдельный публичный
`GET /api/version`. Он не выполняет запросы к PostgreSQL и не запускает
фоновые задачи. Пример ответа:

```json
{ "revision": "a7b8c9d01234" }
```

`GET /api/health` по-прежнему возвращает `ok`, `time` и `revision`, но
также запускает best-effort housekeeping: для проверки версии его
использовать не следует.

Поле `revision` равно первым 12 символам проверенной переменной
`RENDER_GIT_COMMIT`. Если переменная недоступна или имеет неверный формат,
возвращается `null`, а **не** выдуманный коммит. Обработчик выставляет
`Cache-Control: no-store, max-age=0` и `X-Robots-Tag: noindex, nofollow`.
Никакие ключи и остальные переменные окружения не передаются клиенту.

## Безопасная процедура

1. Найдите последний успешный коммит в
   [GitHub Actions](https://github.com/danilaextrem-afk/Bonusgo/actions).
2. Откройте `https://qronus.onrender.com/api/version` в браузере или
   выполните `curl -i https://qronus.onrender.com/api/version`.
3. Сравните поле `revision` с первыми 12 символами SHA успешного коммита.
4. Если не совпадает, проверьте в **своём** Render Dashboard ветку `main`,
   последние Deploys/Events, build/start commands и режим Auto Deploy.
   Render не обязан разворачивать каждый push, если автодеплой отключён,
   настроена другая ветка или деплой завершился ошибкой.
5. Если `revision: null`, проверить SHA этим методом нельзя: проверьте
   переменную `RENDER_GIT_COMMIT` и способ развертывания через панель Render.
6. Если сам URL не отвечает, сначала проверить DNS, sleep/пробуждение
   бесплатного инстанса, логи приложения и работоспособность базы.
   Ошибка DNS одного клиента ещё не означает глобальный отказ сайта.

Для независимой проверки из инфраструктуры GitHub откройте
**Actions → Verify published Render revision → Run workflow** и выберите
ветку `main` после завершения деплоя. Workflow запускает
`scripts/check-render.mjs` и сравнивает `/api/version` с SHA
выбранного коммита. При временном `HTTP 502/503/504` или сетевой ошибке
он повторяет запрос до шести раз с интервалом 10 секунд, но не считает
неудачные запросы успехом. При несовпадении SHA или неверном JSON
проверка немедленно завершается ошибкой. Ответы сервера и секреты
в лог не выводятся.

**На 19 ноября 2026** внешняя проверка `/ru` и `/api/version`
получила `HTTP 503`. Причина не подтверждена: необходимо проверить
события и логи старта Render, настройки ветки и доступность базы.
Зелёный CI сам по себе не подтверждает работоспособность продакшена.
Проверка запускается **только вручную** — не требуется токен Render и
не выполняются платежи.

## Ручной запуск деплоя (после успешного CI)

В репозитории есть отдельный, **неавтоматический** workflow
[Deploy QRonus to Render (manual)](https://github.com/danilaextrem-afk/Bonusgo/actions/workflows/deploy-render.yml).
Он нужен в ситуации, когда GitHub собрал новую версию, а Render продолжает
обслуживать старую сборку.

Владелец должен один раз настроить секрет **в интерфейсе GitHub**:

1. Откройте Render → сервис `qronus` → Settings → **Deploy Hook**.
   Убедитесь, что это именно сервис, обслуживающий `qronus.onrender.com`,
   и он подключён к репозиторию `danilaextrem-afk/Bonusgo`.
2. Скопируйте секретный Deploy Hook **не в чат**, а в
   GitHub → `Bonusgo` → Settings → Secrets and variables → Actions →
   New repository secret с именем `RENDER_DEPLOY_HOOK_URL`.
3. После успешного CI откройте GitHub Actions → **Deploy QRonus to Render
   (manual)** → Run workflow, выберите ветку `main`, введите
   `DEPLOY_QRONUS`.
4. Workflow проверит наличие успешного CI именно для выбранного SHA,
   выполнит локальные тесты безопасности и отправит один POST на
   официальный Deploy Hook с параметром `ref=<SHA>`.
   Ответ `200` означает начало деплоя, `202` — постановку в очередь,
   **но ни то ни другое не доказывает, что новая версия уже открывается**.
5. После завершения события Deploy в панели Render запустите
   **Verify published Render revision**. Совпадение SHA подтверждает,
   что отвечает ожидаемая версия. Если /api/version всё ещё 404,
   проверьте привязку сервиса к репозиторию и логи запуска.

Не создавайте новый Render-сервис вместо существующего и не включайте
платные ресурсы только ради этой операции. Workflow ничего не запускает,
пока владелец явно не подтвердит действие и не настроит секрет.

Никогда не делитесь токенами Render, секретами, строкой подключения к БД
или deploy-hook URL в переписке. Не запускайте платные услуги и не включайте
реальные платежи для выполнения этого шага.

Важно: `/api/version` предназначен для сверки SHA **без побочных эффектов**.
В отличие от него, `/api/health` запускает best-effort housekeeping через
`runDueJobs()`; для диагностики публикации используйте `/api/version`.

## Автотесты

`tests/ops/render-probe.test.mjs` дополнительно проверяет HTTP 503,
сети, повторы и корректность SHA в полностью офлайн-режиме.
`tests/unit/deployment-revision.test.ts` проверяет формат и отсутствие
утечки недоверенного значения. `tests/e2e/health.spec.ts` проверяет
оба ответа локально запущенного приложения, запрет кеширования,
ограниченный набор полей и стабильность SHA при повторных запросах. Эти тесты не подменяют проверку
`qronus.onrender.com` после деплоя.
