# QRonus и Platega

Platega обрабатывает оплату тарифов QRonus в рублях. Реализация поддерживает СБП по QR (метод 2). Лимит суммы заказа составляет 1 000 000 копеек. TOP на 3 и 12 месяцев недоступен через Platega, а PRO на год стоит 9 900 ₽ и входит в лимит.

## Подготовка к согласованию

1. Подтвердить у менеджера подключение СБП, юридический статус продавца, порядок формирования чеков и доступность тестового мерчанта. Предложения 8,5% за СБП и 5% за крипто требуют подтверждения. Криптооплата в QRonus отсутствует.
2. Подтвердить, что провайдер удерживает комиссию с продавца, а покупатель платит сумму счёта без доплаты. Это обязательное условие для заданного лимита. После сверки в кабинете применяется `PLATEGA_SELLER_PAYS_FEE=true`. Значения комиссии из ответа API сохраняются для аудита как данные провайдера.
3. Подготовить staging с тестовой базой. Создать через обычную регистрацию отдельный аккаунт владельца тестовой компании. Передать доступ в закрытом канале Platega и отозвать после проверки. В коде тестовая оплата через mock изолирована от Platega. Публично документированный sandbox URL для этого сценария не подтверждён.
4. Опубликовать проверенные реквизиты и работающую поддержку. В футере текущих исходников предусмотрен код `verplatega`. Проверить его на публичном URL перед передачей ссылки.
5. Установить у провайдера Callback URL `<APP_URL>/api/payments/platega/callback`. Использовать тот же HTTPS-origin в приложении. После одобрения мерчанта и проверок задать ключи через хранилище секретов, проверить готовность чеков и только затем включать `PLATEGA_LIVE_ENABLED`. Образ для Яндекса поставляется с выключенным флагом и включённым деморежимом.

## Как проходит оплата

- Владелец компании проходит сессионную проверку и CSRF. Сумма берётся из серверных тарифов. В `metadata.user_email` передаётся email этого владельца.
- В PostgreSQL регистрируется заказ. Повтор одной формы с тем же ключом использует существующую платёжную ссылку, если заказ ещё ожидает оплаты. Во время запроса к провайдеру этот же ключ блокирует второй запрос. При неопределённом результате запроса новый запрос с тем же ключом запрещён. Сверка в кабинете Platega нужна, если API не вернул идентификатор. Локальный номер счёта передаётся как `payload`.
- `POST /transaction/process` возвращает ID провайдера. Пользователь переходит только на HTTPS-адрес `pay.platega.io`.
- Callback проверяется по `X-MerchantId` и `X-Secret`. Сервер запрашивает `GET /transaction/{id}` и сверяет ID, валюту, сумму и, при наличии, номер счёта и мерчанта. Повторное уведомление обрабатывается в транзакции PostgreSQL и тариф продлевается только один раз.
- Полный подтверждённый возврат отражается в истории. Частичные возвраты, споры, автоматическая сверка при пропуске всех уведомлений и фискальное аннулирование чека остаются задачами перед коммерческим релизом.

Справка провайдера: [создание платежа](https://docs.platega.io/создание-ссылки-на-оплату-29203843e0), [проверка статуса](https://docs.platega.io/проверка-статуса-оплаты-29203844e0), [обзор API](https://docs.platega.io/).
