# QRonus 0.1.0

## Состояние на 20 ноября 2026, МСК

- [Публичный тестовый сайт](https://qronus-staging-l0to.onrender.com/ru) работает на Render. [Тарифы](https://qronus-staging-l0to.onrender.com/ru/tarify) для России: FREE — 0 ₽, PRO — 490 ₽ в месяц, TOP — 990 ₽ в месяц. Белорусские цены не менялись.
- Render опубликовал коммит `53021f081b76fff16a8e6912fdaac4eb8c7060fe` ветки `deploy/qronus-staging`. Публичные `/api/version`, `/api/live` и `/api/ready` вернули 200. Отдельная база PostgreSQL 16 прошла миграции. Бесплатная база истекает 19 декабря 2026 г.
- На публичном адресе прошли 6 сценариев Playwright с Chromium 153: регистрация, создание заведения и бонусной программы, история клиента, начисление, изоляция компаний, тестовая активация PRO, готовность БД и документы с `verplatega`. Локальные 246 тестов на Node.js 22 также прошли.
- На staging включён имитатор оплаты и выключен боевой Platega. Для российского TOP суммы за 1, 3 и 12 месяцев составляют 990 ₽, 2 970 ₽ и 9 900 ₽. Годовой PRO стоит 4 900 ₽. Существующие счета сохраняют зафиксированные суммы.
- Конфигурация staging находится в `render.staging.yaml`, база подключается через Render, реальные данные не переносились. Основной домен `qronus.onrender.com` обслуживает прежнюю сборку. Для постоянного общественного запуска остаются выпуск на Yandex Cloud, проверка документов продавца, одобрение Platega и отдельный контрольный прогон боевого мерчанта.

## Platega и production

- Эта ветка готовит СБП QR. Реальные платежи в ходе работы не включались и не проводились. Доступность публичного API проверялась без ключей. Доступ одобренного мерчанта, действующая комиссия и активный способ оплаты по конкретному договору пока не проверены.
- Тестовые платежи изолированы через mock. Официальный staging/sandbox для конкретного мерчанта требует подтверждения Platega. Код использует публично документированные методы API и заголовки. Детали в [platega.md](platega.md).
- На Render главная, тарифы, вход и старый `/api/health` вернули HTTP 200, а `/api/version`, `/api/live`, `/api/ready` и новая страница оплаты отсутствовали на проверенном URL. Публичный SHA и база на Render не подтверждены. Доступа к журналам и настройкам Render в рамках этой проверки не было.
- Целевая эксплуатация — Yandex Cloud, с PostgreSQL и Lockbox. Облачная ревизия и staging ещё не созданы. Процедура переноса и проверок описана в [DEPLOY_YANDEX.md](DEPLOY_YANDEX.md).
- Перед коммерческим запуском нужны реальные реквизиты, проверенные публичные документы, работающий почтовый канал поддержки и восстановления, решение по чекам и возвратам, тестовый аккаунт проверяющего в отдельной среде и одобрение Platega. Частичный возврат, спор, повторная фискализация и сверка при пропуске всех callback остаются открытыми. Неопределённый POST без ID провайдера сверяется вручную по номеру счёта.

## Локальный запуск и следующий шаг

```bash
npm ci
# Перед миграцией задайте DATABASE_URL для выделенной базы.
npm run db:migrate
APP_URL=http://localhost:3000 npm run dev
```

Для тестов задайте отдельный `DATABASE_URL_TEST` и примените миграции к этой базе. Запускайте E2E с тестовым способом оплаты и отдельным PostgreSQL. Боевые ключи, контактные данные покупателей и строки подключения не передаются в Git.

Следующая задача — развернуть эту release-ветку в **отдельном staging Yandex Cloud** с отключённой Platega и PostgreSQL, выполнить миграции, прогнать три диагностических маршрута и основные пользовательские сценарии через публичный HTTPS-origin. После staging и идентификации продавца передать провайдеру закрытый доступ для согласования.
